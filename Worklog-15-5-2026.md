## Shipping slice — v0.1.5 (live logs, alerts, HTTP discovery) — 2026-05-15

### Date / time

2026-05-15 (wrap-up commit).

### Context

Smoke-test feedback: misleading ping latency wording, noisy HttpClient logs, HTTP checks marking expected responses as DOWN, subnet discovery tied to one manual CIDR, and tray/webhook **spam** from alerting every scheduler poll plus incorrect repeat timing.

### Why this work was done

- Make diagnostics usable in-session (**Logs** tab) without framework noise dominating the grid.
- Align HTTP success with typical redirects/auth setups (**200–399** default; optional explicit codes).
- Stop alert fatigue: **transition-only** incidents, correct **repeat** cadence, **auto-close** on OK.
- Let Discovery reflect **all active IPv4 interfaces** (Wi‑Fi, Ethernet, VPN), not one guessed subnet.

### What changed

- Version **0.1.5** (`Directory.Build.props`, `VERSION`, `README`, `CHANGELOG`).
- Serilog file logging + in-memory UI sink; EF SQL and HTTP client namespaces capped at Warning.
- WPF **Logs** tab (clear / copy / open folder); `UiLogLineVm` + buffer types under `Infrastructure/Logging`.
- `HttpExpectedStatuses` + tests; `HttpCheckParams` extended; ping message clarifies ICMP vs wall time.
- `AlertIncidentTriggers` / `AlertRepeatSchedule`; scheduler + `AlertEngine` + `WpfAlertSink` behavior fixes; stable `Settings` queries (`OrderBy Id`).
- `DiscoveryService` multi-subnet enumeration + merged scan; empty CIDR in UI triggers auto-scan.
- Documentation updates in `docs/index.md` and `docs/architecture.md`.

### Where changes were made

- `src/NextWatch.Core/` — Alerts, Checks, `DependencyInjection`, `CheckSchedulerService`, `DiscoveryService`, related services.
- `src/NextWatch.Core/Infrastructure/Logging/` — `InMemoryUiLogBuffer`, `InMemoryUiLogSink`, `UiLogEntry`.
- `src/NextWatch.Desktop/` — `MainWindow.xaml`, `MainViewModel`, `WpfAlertSink`, onboarding.
- `tests/NextWatch.Core.Tests/` — `HttpExpectedStatusesTests`, `AlertIncidentTriggersTests`, `AlertRepeatScheduleTests`.

### How it was implemented

- **Incidents:** call `ProcessStatusChangeAsync` only when `ShouldOpenNewIncident(previousStatus, currentStatus)`; on persisted **OK**, set `AcknowledgedAtUtc` on open rows for that check.
- **Repeats:** `AlertRepeatSchedule.IsRepeatDue` uses `(RepeatCount + 1) * RepeatMinutes` from original fire time.
- **Escalation:** before inserting a new `AlertEvent`, supersede prior open incidents for the same check.
- **Discovery:** `NetworkInterface` IPv4 unicast addresses + OS prefix → normalized network CIDR; dedupe; ping probe per subnet.

### Tests run

- `dotnet test tests/NextWatch.Core.Tests/NextWatch.Core.Tests.csproj -c Release` — **24 passed**.
- `dotnet build src/NextWatch.Desktop/NextWatch.Desktop.csproj -c Release` — succeeded.

### Known risks / follow-ups

- Older installs may have accumulated duplicate **open** incidents; repeats could linger until acked or DB cleaned once.
- Discovery is still **ICMP-based** and limited by `maxHostsPerSubnet` (default 64 in UI); many devices block ping.
- No desktop editors yet for per-rule `ToastEnabled` or HTTP expected-status strings.
